Setup

4.1 Start Ollama and Pull the Model

In a separate terminal, start the Ollama server and ensure the model is available:

# Start Ollama (keep this terminal open)
ollama serve

# In another terminal, pull the course model if you haven't already
ollama pull llama3.2:3b

(If you use the bundled server instead of Ollama, skip these two commands — start it with python server/server.py and the model auto-downloads.)

4.2 Configure the OpenAI-Compatible Environment Variables

CrewAI is designed to work with the OpenAI API. To use a local Ollama model instead, we configure CrewAI to point at Ollama's OpenAI-compatible endpoint:

cd web-based-course/
source .venv/bin/activate

# Point CrewAI at the local Ollama server's OpenAI-compatible endpoint
export OPENAI_API_BASE=http://localhost:11434/v1

# CrewAI requires an API key even when using local models.
# Ollama does not validate this key — it can be any non-empty string.
export OPENAI_API_KEY=sk-local

# Tell CrewAI which model to use (must match a model exposed by your LLM server)
export OPENAI_MODEL_NAME=Llama-3.2-3B-Instruct-Q4_K_M
Why OPENAI_API_KEY=sk-local?
  • CrewAI internally uses the OpenAI Python SDK, which refuses to initialize without an OPENAI_API_KEY set.
  • Ollama's /v1 endpoint is OpenAI-compatible but does not check authentication — any non-empty string works.
  • The value sk-local is just a convention to make it clear this is a local setup, not a real OpenAI key.
  • If you forget to set this variable, CrewAI will raise an error like AuthenticationError: No API key provided.

The course uses Llama-3.2-3B-Instruct-Q4_K_M (the model served by the bundled server) throughout, so results are directly comparable across labs. Keep OPENAI_MODEL_NAME set to this value unless you have a specific reason to experiment.

4.3 Start the Application

python agents-app/run.py

Open http://localhost:8003. Enter a topic and click "Run Crew" to see the default pipeline execute.

Important: CrewAI makes multiple LLM calls per agent (reasoning loops). With local models, crew runs can take some time to complete.

Concepts You Need to Understand

Agents

An agent is an autonomous entity with:

  • Role — its job title (e.g., "Researcher", "Writer")
  • Goal — what it's trying to achieve (uses {topic} placeholder)
  • Backstory — context that shapes its expertise and personality
  • Tools — external capabilities it can use
  • allow_delegation — whether it can ask other agents for help

How Agents Are Configured: Code vs. Declarative

There is no single industry standard for specifying agents. Two main approaches exist:

1. Programmatic (code-based) — used in this lab: Agents are defined as Python objects. This gives full flexibility, supports conditional logic, and makes the internal structure explicit.

researcher = AgentDefinition(
    role="Researcher",
    goal="Research {topic} thoroughly",
    backstory="You are an expert researcher...",
    tools=[],
    allow_delegation=False,
)

2. Declarative (config-based) — used by many production tools: Agents are defined in YAML, JSON, or Markdown files. The runtime reads the config and constructs agents automatically.

researcher:
  role: "Researcher"
  goal: "Research {topic} thoroughly"
  backstory: >
    You are an expert researcher with 20 years of experience
    finding and synthesizing information from multiple sources.
  tools: []
  allow_delegation: false
AspectCode-basedDeclarative (YAML/Markdown)
FlexibilityFull (conditional logic, dynamic construction)Limited to what the schema supports
ReadabilityRequires programming knowledgeAccessible to non-developers
PortabilityTied to specific framework APIEasier to migrate between tools
Version controlCode diffsClean config diffs
Best forComplex/dynamic pipelines, learningProduction teams, rapid iteration

Tasks

A task is a specific assignment with:

  • Description — detailed instructions for the agent
  • Expected output — what the result should look like
  • Agent role — which agent handles this task
  • Context tasks — previous tasks whose output feeds into this one

Crew

A crew is a team of agents executing tasks together:

  • Sequential process — tasks run one after another, output flows forward
  • Hierarchical process — a manager agent coordinates and delegates

Tools and Their Relationship to MCP

Tools extend agents' capabilities by letting them perform actions: read files, make calculations, query databases, or call other services. A tool is a Python class with a name, description, and a run() method. The agent reads the tool's description to decide when to invoke it.

MCP ConceptLab Equivalent
MCP ServerA tool class (e.g., RAGQueryTool, FileReaderTool) that exposes a capability
Tool declaration (name + description + schema)The tool's name and description fields — the "contract" the agent sees
Tool invocationThe agent calling tool.run(input) during its reasoning loop
Tool resultThe string returned by run(), fed back into the agent's context
Key insight: Tools are the standardized bridge between the agent's LLM reasoning and any external functionality. The agent only sees the description (what it can do) and gets back text (the result). Whether the tool's backend is a local file system, a database, or a remote API is opaque to the agent — exactly the same encapsulation philosophy as MCP.

Execution Flow (Sequential)

User Input ("AI in healthcare")
    → Researcher Agent (research task)
        → produces research brief
    → Writer Agent (writing task, receives research brief)
        → produces article draft
    → Reviewer Agent (review task, receives article draft)
        → produces final polished article
→ Final Output returned to user

Task 3.5 — Build Custom Tools

Files: ai/tools.py, ai/agents.py

📖 Before you start: Read the 🔧 Tools & MCP tab — study "Tool Architecture", "Building Custom Tools", and "How LLM Decides to Use a Tool" topics.

Background

Tools extend agent capabilities beyond pure text generation. Without tools, an agent can only produce text from its training knowledge. With tools, it can count words, read files, perform calculations, or query databases.

A tool is a Python class that extends CrewAI's BaseTool with:

  • name — identifier the agent uses to reference the tool
  • description — the agent reads this to decide when to use the tool
  • _run(input) → str — executes logic and returns a text result

Option B — Hard path (★★★): Implement yourself

Implement tools from scratch in ai/tools.py:

Step 1: Create a WordCountTool

from crewai.tools import BaseTool

class WordCountTool(BaseTool):
    name: str = "word_counter"
    description: str = (
        "Count words, sentences, and paragraphs in text. "
        "Input: the text to analyze. Returns statistics."
    )

    def _run(self, text: str) -> str:
        words = len(text.split())
        sentences = text.count('.') + text.count('!') + text.count('?')
        paragraphs = len([p for p in text.split('\n\n') if p.strip()])
        return f"Words: {words}, Sentences: {sentences}, Paragraphs: {paragraphs}"

Step 2: Create a CalculatorTool

import math

class CalculatorTool(BaseTool):
    name: str = "calculator"
    description: str = (
        "Perform a mathematical calculation. "
        "Input: a math expression like '2 + 2' or 'sqrt(144)'. "
        "Returns the numeric result."
    )

    def _run(self, expression: str) -> str:
        allowed = {'sqrt': math.sqrt, 'round': round, 'abs': abs, 'pow': pow}
        try:
            result = eval(expression.strip(), {"__builtins__": {}}, allowed)
            return f"Result: {result}"
        except Exception as e:
            return f"Error: {str(e)}"

  • Check verbose output — run with verbose=True to see exactly what each agent is thinking and doing.
  • Agent backstory matters more than you think — a detailed backstory significantly improves output quality.
  • Task descriptions should be specific — vague instructions produce vague results. Use numbered steps.
  • Tool descriptions are prompts — the agent reads the description to decide when to use the tool. Make it clear and specific.
  • If the crew fails, check the terminal logs. Common issues: model not found, timeout, malformed tool output.

Design Principles

Designing a multi-agent system starts with decomposing a problem into specialized subtasks, then mapping each subtask to an agent with the right expertise.

Think of it like hiring a team: You wouldn't ask one person to research, write, fact-check, and format. You'd hire specialists for each step.

Step 1: Identify the End Goal

Start with the final output you want. Ask: "What should the user receive at the end?"

  • A well-written article? A fact-checked report? A translated document?
  • A code review with suggestions? A data analysis summary?

Step 2: Work Backwards

Decompose the end goal into sequential stages. Each stage should:

  1. Have a single responsibility — one clear thing it produces
  2. Require specific expertise — a distinct skill set
  3. Build on previous output — take the prior stage's result as input
  4. Produce a concrete artifact — a defined deliverable

Step 3: Map Each Stage to a Role

QuestionMaps to
What is this person's job title?Role
What are they trying to achieve?Goal
What makes them an expert?Backstory
What external resources do they need?Tools

Step 4: Define Task Descriptions with Precision

  • Specific instructions — use numbered steps, not vague directives
  • Expected output format — "a markdown report with headings" not "a good report"
  • Constraints — word limits, required sections, things to avoid
Rule of thumb: If a human reading the task description wouldn't know exactly what to produce, the LLM won't either.

Step 5: Order Tasks by Dependency

Place tasks so each can use the previous task's output as context. Ask: "Can this agent do its job without seeing the previous output?"

Tasks & Pipelines

A task is a specific assignment given to an agent:

  • Description — detailed instructions (use numbered steps)
  • Expected output — the format and content of the result
  • Agent role — which agent handles this task

Tasks form a pipeline: they execute in list order, and each task's output is automatically available to subsequent tasks as context.

Research Task → Writing Task → Review Task

The output of the last task becomes the crew's final output returned to the user.

Execution Order = Task List Order

The sequence of agent invocation is determined by the order of tasks in the list returned by get_tasks() in ai/tasks.py — not by the agent list.

# ai/tasks.py — THIS ORDER defines execution sequence:
return [research_task, writing_task, review_task]
#       ↑ runs first   ↑ runs second  ↑ runs last

Each task has an agent_role field. CrewAI matches it to the corresponding agent by role name (via build_agent_map). The agent list order in get_agents() does not matter — agents are looked up by name, not position.

Important: If you swap the order to [writing_task, research_task, review_task], the Writer would run first (without research context). It would execute — but produce poor results because it lacks input from the Researcher.

What Are Agents?

An agent is an autonomous entity powered by an LLM that can reason, plan, and take actions. Unlike a simple chatbot that responds to a single prompt, an agent operates in a loop:

  1. Observe — receive a task or input
  2. Think — reason about what to do (the LLM generates a plan)
  3. Act — execute an action (use a tool, delegate, or produce output)
  4. Repeat — iterate until the task is complete

In CrewAI, each agent is defined by its role, goal, and backstory — these shape how the LLM behaves when acting as that agent.

Key insight: The agent is not the LLM itself. The agent is a configuration that instructs the LLM how to behave for a specific purpose.

Roles, Goals & Backstories

Each agent has three identity fields that together form its "persona":

FieldPurposeExample
RoleJob title — what the agent is"Researcher", "Writer", "Fact-Checker"
GoalWhat it's trying to achieve (uses {topic})"Gather comprehensive information on {topic}"
BackstoryContext, expertise, and personality"You are an experienced research analyst with 20 years..."

The backstory has a surprisingly large effect on output quality. A detailed backstory produces more focused, expert-level responses.

Crew Assembly

A crew brings agents and tasks together into an executable unit:

crew = Crew(
    agents=[researcher, writer, reviewer],
    tasks=[research_task, write_task, review_task],
    process=Process.sequential,
    verbose=True,
)
result = crew.kickoff(inputs={"topic": "AI in healthcare"})

The crew handles:

  • Matching tasks to their assigned agents (by role name)
  • Passing output from one task to the next as context
  • Managing agent reasoning loops (3-10 LLM calls per task)
  • Collecting and returning the final output
Key point: CrewAI is an orchestration framework, not middleware. It actively drives execution - owning control flow, reasoning loops, and inter-agent coordination.

Execution Modes

Sequential (default)

Task 1 (Researcher)→Task 2 (Writer)→Task 3 (Reviewer)

Tasks run in list order. Each agent works independently. Output flows forward.

Hierarchical

Manager↔Researcher↔Writer↔Reviewer

A manager agent coordinates - deciding task order, reviewing outputs, reassigning work. More LLM calls but better for complex tasks.

Delegation

When allow_delegation=True, an agent can ask another for help mid-task. It is a nested function call: Agent A pauses, Agent B runs its full loop, returns a string, Agent A resumes.

Comparison

AspectSequentialHierarchical
Task orderFixedManager-decided
LLM calls3-10 per agent~2x (manager overhead)
Best forLinear pipelinesComplex/adaptive workflows
Advice: Start sequential. Avoid delegation with local models - it multiplies LLM calls.

The Execution Loop

No parallelism, no threads, no IPC. The entire crew runs as sequential function calls in one thread:

results = {}
for task in tasks:
    agent = task.assigned_agent
    context = gather_previous_outputs(results)
    scratchpad = []
    while not done and iterations < max_iter:
        response = litellm.completion(
            model="openai/Llama-3.2-3B-Instruct-Q4_K_M",
            messages=build_prompt(agent, task, context, scratchpad)
        )
        if response.has_tool_call:
            result = tool.run(response.tool_input)
            scratchpad.append(result)
        elif response.has_final_answer:
            done = True
        iterations += 1
    results[task] = response.final_answer

Agent Communication = String Passing

  1. Agent 1 finishes → output string
  2. String concatenated into Agent 2's prompt as context
  3. Agent 2 reads it as input

Tool execution<1 sec0-3 per agent

Key realization: "Multi-agent" is a loop calling an LLM with different system prompts. Agents are prompt configurations that take turns.

Internal Prompt Templates

CrewAI has hardcoded prompt templates in crewai/translations/en.json that define how your agent and task definitions are assembled into the actual LLM prompt. Understanding these reveals exactly how your role, goal, backstory, and task.description get used.

System Message Template

The agent's identity is constructed using the role_playing template:

"role_playing": "You are {role}. {backstory}\nYour personal goal is: {goal}"

So if you define:

AgentDefinition(
    role="Researcher",
    goal="Gather comprehensive information on {topic}",
    backstory="You are an experienced research analyst..."
)

The system message sent to the LLM becomes:

You are Researcher. You are an experienced research analyst...
Your personal goal is: Gather comprehensive information on AI trends

Format Instructions (No Tools)

When an agent has no tools, CrewAI appends the no_tools template:

"no_tools": "To give my best complete final answer to the task
use the exact following format:

Thought: I now can give a great answer
Final Answer: Your final answer must be the great and the most
complete as possible, it must be outcome described.

I MUST use these formats, my job depends on it!"

This forces the agent to produce a structured "Final Answer" output.

Format Instructions (With Tools)

When an agent has tools, CrewAI uses the tools template instead — the ReAct format:

"tools": "You ONLY have access to the following tools,
and should NEVER make up tools that are not listed here:

{tools}

Use the following format:

Thought: you should always think about what to do
Action: the action to take, only one name of [{tool_names}],
  just the name, exactly as it's written.
Action Input: the input to the action, just a simple python
  dictionary, enclosed in curly braces, using \" to wrap keys and values.
Observation: the result of the action

Once all necessary information is gathered:

Thought: I now know the final answer
Final Answer: the final answer to the original input question"

How Task Description Is Injected

The task's description and expected_output are added to the user message. The full prompt the LLM receives looks like:

# SYSTEM MESSAGE (from role_playing template)
You are {role}. {backstory}
Your personal goal is: {goal}

# USER MESSAGE (assembled by CrewAI)
Current Task: {task.description}

This is the expected criteria for your final answer:
{task.expected_output}

{format_instructions}  ← either no_tools or tools template

{context from previous tasks if any}

Key Implications

  • Backstory is literally the system prompt — it's the first thing the LLM reads after "You are {role}."
  • Goal becomes a directive — "Your personal goal is:" frames it as an instruction
  • Task description is the user message — this is what the LLM treats as the "question to answer"
  • Expected output constrains the format — placed as "expected criteria" before format instructions
  • You cannot change these templates without modifying the crewai package — but understanding them helps you write more effective agents and tasks
Practical tip: Since CrewAI adds "Your personal goal is:" before your goal text, don't repeat phrasing like "My goal is to..." — just state the objective directly: "Gather comprehensive information on {topic}".

Error Correcting Prompts

When running the crew with local models, you may observe that an agent's first LLM call produces no useful output — just a parroted format template — followed by a retry that produces the actual answer. This is CrewAI's error correction mechanism in action.

What Happens

  1. First call: The LLM receives the task + format instructions. With small local models (few-billion parameters, like the course 3B), the LLM sometimes parrots the format template instead of doing actual work: 
    Thought: I now can give a great answer
Final Answer: [empty or repeats the template]
  2. Parser detects failure: CrewAI's parser (in crewai/agents/parser.py) checks if the output matches the required format. When it doesn't, it generates an error correction message.
  3. Retry call: The error message is appended to the conversation and sent back to the LLM: 
    "I did it wrong. Invalid Format: I missed the 'Action:'
after 'Thought:'. I will do right next, and don't use
a tool I have already used."
  4. LLM corrects itself: On the second attempt, the LLM understands it needs to produce actual content and generates the real answer.

Built-in Error Messages

CrewAI defines these in crewai/agents/parser.py:

ErrorTrigger
"I missed the 'Action:' after 'Thought:'"LLM wrote Thought but no Action or Final Answer
"I missed the 'Action Input:' after 'Action:'"LLM wrote Action but no input
"Tried to both perform Action and give Final Answer"LLM produced both in the same response

Why This Happens with Local Models

Small local models (few-billion parameters, like the course 3B) sometimes interpret format instructions as content to repeat rather than meta-instructions about output structure. They see:

Thought: I now can give a great answer
Final Answer: Your final answer must be the great and the most complete...

And copy it verbatim, thinking that IS the answer. Much larger models rarely do this because they've seen more varied training examples of format instructions vs actual content.

Impact on Performance

  • Each retry adds 5–30 seconds (one extra LLM call)
  • Typically happens once per agent on the first call
  • CrewAI caps retries at max_iterations (default: 10)
  • You can observe this in the execution log: look for consecutive [LLM_INPUT] calls for the same agent with the error text in the user message

Mitigations

  • Write explicit task descriptions — make it clear the agent should produce substantial content, not just acknowledge the task
  • Accept the overhead — one retry per agent is normal with the course 3B model (~10-15 extra seconds total)
Observation exercise: Run the crew and watch the execution log. Count how many [LLM_INPUT] calls each agent needs. If you see 2 calls for an agent, the first was likely a format error retry. Try improving your task description to reduce retries.

Why Correction Works — From the Training Perspective

The LLM doesn't "understand" anything — it predicts the next token based on statistical patterns from training data.

First call — why it parrots

The model sees a prompt ending with format instructions like Thought: I now can give a great answer / Final Answer: Your final answer must be.... From training, the model learned that when text contains "Thought:" followed by "Final Answer:", the highest-probability continuation is to repeat/continue that pattern. The format template looks like an example completion, so the model predicts tokens that continue the example rather than generating novel content.

Second call — why correction shifts the probability

The conversation now contains: (1) original prompt, (2) the bad first response, (3) error message "I did it wrong..."

From RLHF (Reinforcement Learning from Human Feedback) training, the model learned:

  • When a conversation contains "I did it wrong" / correction feedback → the next response should be a revised, substantive attempt
  • The conditional probability P(substantive answer | previous_error + correction) is much higher than P(repeat template | previous_error + correction)
  • Training data showed that after corrections, likely continuations are actual content — not repeated errors

The error correction message shifts the token probability distribution toward substantive content, because the model was trained on many examples where corrections led to better outputs.

Why larger models don't need this

  • Much larger models have seen more varied training examples of format instructions vs actual content
  • They better distinguish "this is a template to follow" from "this is text to copy"
  • Their larger parameter space can represent the subtle statistical difference between meta-instructions and content to generate
Key insight: Error correction in CrewAI works not because the LLM "learns" from the mistake, but because the correction text shifts the statistical context into a region of token-probability space where substantive content is the most likely continuation.

Tool Architecture

Tools extend agent capabilities beyond pure text generation. Without tools, an agent can only produce text from its training knowledge. With tools, it can query databases, read files, perform calculations, or call APIs.

A tool is a Python class with three components:

  • name — identifier the agent uses to reference the tool
  • description — the agent reads this to decide when to use the tool
  • run(input) → str — executes logic and returns a text result
class RAGQueryTool:
    name = "rag_query"
    description = (
        "Query the document knowledge base. Input should be "
        "a search question. Returns relevant document excerpts."
    )

    def run(self, query: str) -> str:
        results = vector_store.similarity_search(query, k=3)
        return "\n".join([doc.page_content for doc in results])

The agent sees only name and description. It decides whether to use the tool based on the description, then passes input. The result string goes back into the agent's scratchpad.

Key insight: The tool's description is a prompt — the agent reads it to decide when to invoke the tool. A clear, specific description means the agent uses it at the right time. A vague one means the agent guesses.

MCP Relationship

The tool architecture in CrewAI mirrors the Model Context Protocol (MCP) — a standard for exposing capabilities to LLM agents:

MCP ConceptCrewAI EquivalentPurpose
MCP ServerA tool classExposes a capability
Tool declaration (name + schema)name + descriptionContract the agent sees
Tool invocationtool.run(input)Execute the capability
Tool resultString returned by run()Fed back into agent context

In both MCP and CrewAI, the agent only sees a self-describing interface. Whether the tool's backend is a local file system, a database, or a remote API is opaque to the agent — same encapsulation philosophy.

This lab does not use the formal MCP transport layer (JSON-RPC over stdio/SSE), but teaches the same design pattern: expose capabilities as discoverable, self-describing tools that an LLM agent can choose to invoke.

Tool Execution in Pipeline

When an agent decides to use a tool during its ReAct loop:

  1. LLM outputs: Action: rag_query + Action Input: AI ethics research
  2. CrewAI parser extracts tool name and input
  3. tool.run("AI ethics research") executes locally
  4. Result string appended to scratchpad as "Observation"
  5. Next LLM call sees the observation and decides: use another tool or produce Final Answer

Building Custom Tools

To create a new tool:

  1. Create a class with name, description, and run(self, input: str) → str
  2. Register it in the tool map in ai/agents.py
  3. Add the tool name to an agent's tools list
# ai/tools.py — define the tool
class WordCountTool:
    name = "word_counter"
    description = (
        "Count words, sentences, and paragraphs in text. "
        "Input: the text to analyze. Returns statistics."
    )

    def run(self, text: str) -> str:
        words = len(text.split())
        sentences = text.count('.') + text.count('!') + text.count('?')
        return f"Words: {words}, Sentences: {sentences}"

# ai/agents.py — register and assign
tool_map = {"word_counter": WordCountTool(), ...}

reviewer = AgentDefinition(
    role="Reviewer",
    tools=["word_counter"],  # Agent can now use this tool
    ...
)

Best Practices

  • Description is everything — write it as if explaining to a colleague what the tool does and when to use it
  • Return text — tools always return strings; the agent reads the result as text
  • Keep tools focused — one tool, one responsibility
  • Limit tool count — too many tools means larger prompts and confused agents
  • Security — validate/sanitize inputs, restrict file paths, avoid eval()

How LLM Decides to Use a Tool

Nobody explicitly commands the LLM to use a tool. The decision is autonomous, driven by the system prompt that CrewAI constructs behind the scenes.

What the LLM Sees

When CrewAI sends a request to the LLM, the prompt includes a section like:

You have access to the following tools:

word_counter: Count words, sentences, and paragraphs in text.
              Input: the text to analyze. Returns statistics.

To use a tool, respond with:
  Action: word_counter
  Action Input: <your input here>

When you're done, respond with:
  Final Answer: <your response>

The Decision Process

The LLM decides based on three inputs:

  1. The task description — e.g., "Review the article and provide word count statistics"
  2. The tool description — tells the LLM what the tool can do
  3. The LLM's reasoning — it connects the task requirement to the available tool

The reasoning goes: "My task requires word count statistics → I have a word_counter tool available → I should use it to get accurate counts rather than guessing."

Who Gives the Command?

No human is in the loop at execution time. The task description is effectively the "command." If the task doesn't require counting words, a capable LLM might never invoke the tool — it only uses tools when its reasoning concludes they'd help fulfill the task.

Key insight: Write clear task descriptions that imply tool usage. If you want the Reviewer to count words, write the task as "Review the content and report word/sentence statistics." The LLM will connect the dots.

The Full Loop

  1. CrewAI sends system prompt + task + tool descriptions to LLM
  2. LLM reasons about the task and decides a tool would help
  3. LLM outputs Action: word_counter + Action Input: <text>
  4. CrewAI parses the output, finds the tool by name, calls tool.run(input)
  5. The returned string is injected back as an Observation
  6. LLM uses the observation to continue reasoning or produce its Final Answer
