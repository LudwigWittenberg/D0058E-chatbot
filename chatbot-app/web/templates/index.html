Step 1: The Problem — Predict the Next Word

At its core, every language model solves one deceptively simple problem:

Given a sequence of words, predict the next word.

That's it. Every chatbot response, every code completion, every AI-generated email — it all reduces to predicting one word at a time, over and over. ChatGPT doesn't "think" or "plan" — it just picks the most likely next word, appends it, and repeats.

Humans Do This Effortlessly

You already solve this problem thousands of times per day without noticing:

SequenceYou predict...
"I drink my morning ..."coffee / tea
"New ..."York
"The chicken didn't cross the road because it ..."was too tired

First Attempt: Count Word Sequences (n-grams)

The simplest machine approach: look at millions of documents, count how often word sequences appear, then estimate "what comes next?" from those counts.

An n-gram is just a sequence of n consecutive words:

  • 2-gram (bigram): "New York"
  • 5-gram: "I drink my morning coffee"
  • 10-gram: "I drink my morning coffee but airplane crashed and nobody ..." (rare/unseen)

In plain English: count how many times you've seen "I drink my morning coffee" vs "I drink my morning tea" in all available texts. Whichever appears more often wins.

The probability of the next word given previous words:

$$P(\text{next word} \mid \text{previous words}) \approx \frac{\text{count(previous words + next word)}}{\text{count(previous words)}}$$

The formal version (same idea, just with symbols for word positions):

$$P(t_{i+1} \mid t_{i-n+1} \ldots t_i) \approx \frac{\#(t_{i-n+1} \ldots t_i,\; t_{i+1})}{\#(t_{i-n+1} \ldots t_i)}$$

The Fatal Flaw: Sparsity

This counting trick works for short, common phrases. But for longer or unusual sentences, the count is zero — you've never seen that exact sequence before:

  • "I drink my morning" → appears in many texts ✓
  • "I drink my morning coffee but the airplane crashed and nobody" → has never been written before ✗
The fundamental problem: most sentences have never been written before. You can't count what doesn't exist. Even the entire internet isn't big enough to contain every possible 10-word sequence.

What Humans Use (That Simple Counting Can't Capture)

When you predict the next word, you're not searching a database of memorized sentences. You use three types of knowledge:

1. World Knowledge — You understand cause and effect

"If you drop a glass on a stone floor, it will ..."  → "shatter" / "break"

You know glass is fragile and stone is hard. No amount of word counting captures this physical reasoning — you need to understand the world.

2. Grammar — You know what type of word fits

"The device that I bought yesterday and returned today was ..."  → expects adjective: "defective", "broken", "faulty"

You know "was ..." requires an adjective here, even if you've never seen this particular sentence. Grammar gives you constraints.

3. Meaning — You group words by category

"I drink my morning coffee, but my friend drinks morning ..."  → expects similar beverage: "tea"

You know "coffee" and "tea" belong to the same group (beverages). The parallel sentence structure tells you another beverage should go here.

The Challenge for Language Models

A good language model needs all three: world knowledge, grammar, and meaning. Simple counting gives you none of them. This is why we need neural networks — they can learn these patterns from data.

Human predictionUses grammar + meaning + world knowledgeCan't scale to millions of documents

Step 2: Semantic Vectors of Words

The key idea: instead of treating words as arbitrary labels (word #4523 = "cat"), we represent each word as a list of numbers (a vector) that encodes its meaning. Think of it as GPS coordinates — but for meaning rather than location.

In this simplified 2D picture, words are placed on a map where the horizontal axis represents gender and the vertical axis represents age. Words with similar meanings are close together. "Man" and "woman" are at the same height (both adults) but differ horizontally (gender). This geometric layout encodes meaning.

Each word is represented as an arrow (vector) from the origin. Two arrows pointing in a similar direction mean similar words. "Man" and "grandfather" point roughly the same way (both male). "Boy" and "girl" point in different directions (opposite gender).

Real word vectors have hundreds of dimensions (not just 2) — capturing many properties at once: topic, formality, tense, sentiment, and more.

Core Definitions

A vector is simply a list of numbers. If the list has d numbers, we call it a "d-dimensional vector":

$$\mathbf{a} = (a_1, a_2, \ldots, a_d) \in \mathbb{R}^d$$

Dot Product — Measuring Similarity

The dot product is the simplest way to ask "how similar are these two vectors?" You multiply matching positions and add up:

$$\langle \mathbf{a}, \mathbf{b} \rangle = \sum_{k=1}^{d} a_k \cdot b_k = \text{sim}(\mathbf{a}, \mathbf{b})$$

Large result = vectors are similar. Zero = unrelated. Negative = opposite.

Binary Vector Examples

With simple 0/1 vectors, the dot product just counts how many positions match:

Vectorssim(a,b)Interpretation
a=(1,0,1,0,1), b=(0,1,0,1,0)0Nothing in common
c=(1,0,1,1,1), d=(1,1,1,0,1)3Share 3 features — quite similar

Cosine Similarity — Direction Matters, Not Length

Cosine similarity checks if two arrows point the same direction, regardless of how long they are:

$$\cos(\mathbf{a}, \mathbf{b}) = \frac{\langle \mathbf{a}, \mathbf{b} \rangle}{|\mathbf{a}| \cdot |\mathbf{b}|}$$

where $|\mathbf{a}| = \sqrt{\sum_k a_k^2}$ is the length of the arrow.

Result is always between $-1$ and $+1$:

  • $+1$ → same direction (identical meaning)
  • $0$ → perpendicular (unrelated)
  • $-1$ → opposite direction (opposite meaning)

Distance vs. Similarity

You can also measure how far apart two vectors are (Euclidean distance). The connection is simple — high similarity = small distance:

$$|\mathbf{a} - \mathbf{b}|^2 = |\mathbf{a}|^2 + |\mathbf{b}|^2 - 2\langle \mathbf{a}, \mathbf{b} \rangle$$

Geometric Intuition

ConfigurationCosineMeaning
Arrows point same directioncos ≈ +0.9Very similar words
Arrows at right anglescos = 0Unrelated words
Arrows point oppositecos ≈ −0.8Opposite meanings

Why Vector Arithmetic Works for Analogies

Because meaning is encoded as direction, you can do "meaning arithmetic":

$$\text{sim}(\mathbf{a},\; \mathbf{a}+\mathbf{b}+\mathbf{c}) = \text{sim}(\mathbf{a},\mathbf{a}) + \text{sim}(\mathbf{a},\mathbf{b}) + \text{sim}(\mathbf{a},\mathbf{c})$$

This is why $\text{vec}(\text{king}) - \text{vec}(\text{man}) + \text{vec}(\text{woman}) \approx \text{vec}(\text{queen})$ works — the "male" direction is subtracted, the "female" direction is added, landing near "queen".

Why this matters: Word vectors turn 200,000 unrelated word labels into a space where meaning is distance and analogy is arithmetic. This is the foundation that lets neural networks generalize — if it learns something about "coffee," it automatically applies to "tea" because they're nearby in vector space.

Step 3: The Neural Next-Word Predictor

The Idea

Now we combine Steps 1 and 2: build a system that uses word vectors to predict the next word. The setup:

  • Vocabulary: 200,000 words/tokens (every word the model knows)
  • Embedding table E: a lookup table that gives each word its vector (its "meaning coordinates")
  • Prompt vector p: add up all the input word vectors — this represents the overall meaning of what you typed
  • Weight matrix W: a collection of "prototype" vectors, one for each word — representing "what prompts typically look like before this word"

The prediction process in plain English: look up vectors for each input word, add them up into one summary vector, then find which word's prototype is most similar to that summary.

$$t^{(k)} \mapsto \mathbf{x}^{(k)} = \mathbf{E}[:, k] \in \mathbb{R}^d$$

$$\mathbf{p} = \mathbf{x}_1 + \mathbf{x}_2 + \ldots + \mathbf{x}_L \in \mathbb{R}^d$$

$$s^{(k)} = \text{sim}(\mathbf{p}, \mathbf{w}^{(k)}) \quad \text{for each word } k$$

$$\hat{y} = \text{argmax}_k \; s_k \quad \rightarrow \text{ predicted next word}$$

Both E and W are big tables of numbers: d rows (vector dimensions) × 200,000 columns (one per word). Each column is a word's vector.

Forward Pass (How Prediction Works)

  1. Words → IDs: Convert each word to its number ("cat" → 4523)
  2. Lookup: Get the vector for each word from table E
  3. Add up: Sum all word vectors into one prompt vector p
  4. Compare: Check similarity of p against all 200,000 word prototypes in W — highest score wins

Single-Layer Predictor

This is one big matrix multiplication: the prompt vector p goes in, gets compared against every word's prototype vector in W, and 200,000 similarity scores come out. The word with the highest score is the prediction.

Training: Learn by Mistakes (Punish / Reward)

How does the model learn? Feed it millions of real sentences, let it guess the next word, and when it's wrong — adjust:

If $\hat{y} \neq y$ (prediction wrong):

$$\mathbf{W}[:, y] \leftarrow \mathbf{W}[:, y] + \eta \cdot \mathbf{p} \quad \text{(reward correct word — make more similar to prompt)}$$

$$\mathbf{W}[:, \hat{y}] \leftarrow \mathbf{W}[:, \hat{y}] - \eta \cdot \mathbf{p} \quad \text{(punish wrong word — push away from prompt)}$$

$\eta$ = learning rate (a small number like 0.001 — controls how big each adjustment is). After millions of such corrections, W ends up encoding "for each word, what context typically precedes it."

Multi-Layer Extension (Adding a Hidden Layer)

A single matrix can only learn simple patterns. Adding a hidden layer in the middle lets the network combine features in complex ways (like recognizing "verb + object" patterns):

Forward pass (how it predicts):

$$\mathbf{h} = \sigma(\mathbf{W}_1 \cdot \mathbf{p}) \quad \text{(hidden layer: detect patterns, apply nonlinearity } \sigma \text{)}$$

$$\text{Prob} = \text{softmax}(\mathbf{W}_2 \cdot \mathbf{h}) \quad \text{(convert to probabilities summing to 1)}$$

$$\text{Cost} = -\log \text{Prob}_y \quad \text{(how wrong was the prediction?)}$$

Backpropagation (how it learns — adjusting weights to reduce cost):

$$\boldsymbol{\delta} = \text{Prob} - \mathbf{e}_y \quad \text{(error signal)}$$

$$\frac{\partial \text{Cost}}{\partial \mathbf{W}_2} = \boldsymbol{\delta} \cdot \mathbf{h}^T \quad \rightarrow \text{adjust output weights}$$

$$\frac{\partial \text{Cost}}{\partial \mathbf{W}_1} = (\mathbf{W}_2^T \boldsymbol{\delta} \odot \sigma'(\mathbf{W}_1 \mathbf{p})) \cdot \mathbf{p}^T \quad \rightarrow \text{adjust hidden weights}$$

Key insight: After training on millions of examples, the word vectors in E become the semantic vectors from Step 2 — similar words end up with similar vectors, not because we told the model about similarity, but because predicting correctly requires grouping similar words together.

Understanding the Weight Matrices

The weight matrices store everything the model has learned. They are the model's knowledge — billions of numbers, adjusted by millions of training examples.

Single-Layer: W

$\mathbf{W} \in \mathbb{R}^{d \times |\text{Voc}|}$ — think of each column as a "wanted poster" for a word: "this is what a prompt looks like when I should be predicted next."

  • To predict: compare the prompt against every column (every wanted poster)
  • Best match wins
  • Each column answers: "what context do I typically follow?"

Parameter count: $d \times |\text{Voc}| = 4096 \times 200{,}000 = 819$ million numbers (just for this one table!)

Multi-Layer: W₁ and W₂

With two layers, the work splits into detecting patterns (W₁) and mapping patterns to words (W₂):

MatrixWhat it doesAnalogy
W₁Input → Hidden: detect meaningful patternsLike recognizing "this prompt is asking a question"
W₂Hidden → Output: map patterns to wordsLike knowing "questions are followed by answers"

Why two layers are better: a single layer can only draw straight-line boundaries between word groups. Two layers with a nonlinearity σ between them can learn complex, curved boundaries — capturing subtle patterns like "this word fits here only if the subject was plural."

Step 4: ChatGPT's Self-Attention (From Simplified to Real)

The Problem with Adding Everything Up

In Step 3, we summed all word vectors equally: p = x₁ + x₂ + ... + x_current. But this is like reading an entire paragraph and giving every word equal importance. In reality, when predicting the next word, some earlier words matter much more than others.

Attention: Focus on What Matters

Attention replaces the equal sum with a weighted sum — each word gets an importance weight ($\alpha$). Most weights are near zero; only a few relevant words get high weights:

$$\mathbf{c}_{\text{current}} = \alpha_1 \mathbf{x}_1 + \alpha_2 \mathbf{x}_2 + \ldots + \alpha_{\text{current}} \mathbf{x}_{\text{current}}$$

$\alpha_j$ = "how much should we pay attention to word $j$?" Most $\alpha_j \approx 0$, only a few are large.

How to compute $\alpha$: measure similarity between current position and each earlier word, then normalize (softmax makes them sum to 1):

$$\boldsymbol{\alpha} = \text{softmax}(\mathbf{s}/\sqrt{d}) \quad \text{where } \mathbf{s} = (\text{sim}(\mathbf{q}, \mathbf{x}_1), \ldots, \text{sim}(\mathbf{q}, \mathbf{x}_{\text{current}}))$$

In practice, only 2-3 earlier words typically get large weights — the model learns which words are relevant for each prediction.

Query, Key, Value — The Three Roles

The real Transformer doesn't compare raw word vectors. It first transforms each word into three different "views" — like asking three different questions about the same word:

$$\mathbf{q}_i = \mathbf{x}_i \mathbf{W}^Q \quad \text{(query: "what am I looking for?")}$$

$$\mathbf{k}_j = \mathbf{x}_j \mathbf{W}^K \quad \text{(key: "what do I contain?")}$$

$$\mathbf{v}_j = \mathbf{x}_j \mathbf{W}^V \quad \text{(value: "what information do I carry?")}$$

The attention weight tells how well word $j$ answers position $i$'s question:

$$\alpha_{ij} = \text{softmax}\left(\frac{\text{sim}(\mathbf{q}_i, \mathbf{k}_j)}{\sqrt{d}}\right)$$

Context Vector — The Focused Summary

The context vector at position i is a weighted combination of relevant word values — like a personalized summary of the prompt for that specific position:

$$\mathbf{c}_i = \sum_{j \leq i} \alpha_{ij} \cdot \mathbf{v}_j$$

The Attention Matrix

When we compute attention for all positions at once, we get a matrix where each row shows "who does this position pay attention to?":

$$\mathbf{C} = \text{softmax}\left(\frac{\mathbf{Q}\mathbf{K}^T}{\sqrt{d}}\right) \mathbf{V}$$

Causal (Masked) Attention — No Peeking Ahead

When generating text, position 5 can only look at positions 1-5 (not position 6, which hasn't been generated yet). This is enforced by masking — zeroing out the "future" part of the attention matrix, making it triangular.

The Learned Transforms (Wᵠ, Wᴷ, Wⱽ)

These three matrices are learned during training. They determine what the model considers "relevant":

MatrixRoleAnalogy
Wᵠ (d×d)Query transform"What question does this position ask?"
Wᴷ (d×d)Key transform"What label does this word carry?"
Wⱽ (d×d)Value transform"What information does this word pass along?"
Key insight: Attention lets the model dynamically decide which earlier words matter for each prediction — not a fixed rule, but learned from data. The same word "bank" will attend to different context depending on whether the text is about rivers or finance.

Step 5: Real Transformer and Its Training — Lift Up

Step 4 showed one attention mechanism. The real Transformer scales this up into a repeating building block with three improvements: multiple attention heads (look for different things simultaneously), feed-forward layers (store factual knowledge), and residual connections (keep the original signal so nothing gets lost).

One Transformer Block

Input

A table of word vectors — one row per token in your prompt:

$$\mathbf{X}^{\ell} \in \mathbb{R}^{L \times d_{\text{model}}} \quad \text{(e.g., 1000 tokens} \times \text{4096 dimensions)}$$

Self-Attention (with Layer Normalization)

First, normalize the vectors (keeps training stable), then compute attention. Each "head" looks for different patterns:

$$\mathbf{Q}_h = \text{LN}(\mathbf{X}^{\ell}) \cdot \mathbf{W}_{Q,h}, \quad \mathbf{K}_h = \text{LN}(\mathbf{X}^{\ell}) \cdot \mathbf{W}_{K,h}, \quad \mathbf{V}_h = \text{LN}(\mathbf{X}^{\ell}) \cdot \mathbf{W}_{V,h}$$

$$\mathbf{A}_h = \text{softmax}\left(\frac{\mathbf{Q}_h \mathbf{K}_h^T}{\sqrt{d_k}}\right), \quad \mathbf{O}_h = \mathbf{A}_h \mathbf{V}_h$$

Combine All Heads + Skip Connection

Concatenate outputs from all heads, then add back the original input (residual/skip connection — so information from earlier steps isn't lost):

$$\text{Attn}(\mathbf{X}^{\ell}) = \text{Concat}(\mathbf{O}_1, \ldots, \mathbf{O}_H) \cdot \mathbf{W}_O$$

$$\mathbf{Y} = \mathbf{X}^{\ell} + \text{Attn}(\mathbf{X}^{\ell}) \quad \leftarrow \text{skip connection}$$

Feed-Forward Network (FFN) — The Knowledge Store

Applied to each token independently. This is where factual knowledge lives (expand to wider dimension, apply nonlinearity, compress back):

$$\text{FFN}(\mathbf{z}) = \mathbf{W}_2 \cdot \sigma(\mathbf{W}_1 \cdot \mathbf{z})$$

$$\mathbf{X}^{\ell+1} = \mathbf{Y} + \text{FFN}(\text{LN}(\mathbf{Y})) \quad \leftarrow \text{another skip connection}$$

Multiple Heads — Look for Different Things at Once

Each head has its own W_Q, W_K, W_V — so each head learns to focus on different relationships:

HeadWhat it might specialize in
Head 1Grammar: "does the verb agree with the subject?"
Head 2Coreference: "what does 'it' refer to?"
Head 3Formatting: "are we inside a code block?"
Head 4Topic: "what is this paragraph about?"

Stack Many Blocks Deep — Build Understanding Layer by Layer

A full model repeats this block N times (32-96 blocks in modern models). Each layer builds on the previous one, capturing increasingly complex patterns:

DepthWhat it capturesAnalogy
Layers 1–5Syntax, word orderSpell-checking
Layers 6–15Phrase meaning, who-does-whatSentence parsing
Layers 16–30Reasoning, facts, logicUnderstanding
Final layersFormatting the outputWriting style

Training — Learn by Reading the Internet

The model reads trillions of tokens of text with one simple objective: predict the next token. Every mistake adjusts all weight matrices simultaneously (backpropagation):

$$\text{Cost} = -\sum_{i=1}^{L} \log P(t_i \mid t_1, \ldots, t_{i-1})$$

(Maximize the probability the model assigns to the actual next word.)

All weight matrices in all layers get adjusted: $\mathbf{E}$ (word vectors), $\mathbf{W}_Q, \mathbf{W}_K, \mathbf{W}_V$ (attention), $\mathbf{W}_O$ (head merge), $\mathbf{W}_1, \mathbf{W}_2$ (FFN), plus normalization parameters.

Scale: production LLMs range from a few billion to hundreds of billions of parameters. The course model (Llama-3.2-3B) sits at the small end — enough to run on a laptop, capable enough to see all the same patterns.

The full pipeline: Input tokens → Word vectors → [Transformer Block × N] → Normalize → Score all 200k words → Softmax → Pick next word. Each block: Normalize → Multi-Head Attention → Skip → Normalize → FFN → Skip.

Step 6: Real Transformer at Work — Generation and Inference

Now the model is trained. How does it actually generate text? It works like a very fast typist that picks one word at a time: read what's been written so far, predict the next word, add it to the text, repeat.

From Prompt to Next Word

You type a prompt. The model processes all tokens at once (the "prefill" step) and produces a score for every word in its vocabulary (200,000 scores). Then softmax converts these into probabilities:

$$\text{Prompt tokens } t_{1:k} \rightarrow \text{logits } \mathbf{z}_k \in \mathbb{R}^{|\text{Voc}|}$$

$$P(\text{next word} \mid \text{prompt}) = \text{softmax}(\mathbf{z}_k)$$

The whole response is generated one word at a time (autoregressive):

$$P(\text{full text}) = P(\text{word}_1 \mid \text{prompt}) \times P(\text{word}_2 \mid \text{prompt}+\text{word}_1) \times \ldots$$

Choosing the Next Word — Decoding Strategies

Once we have probabilities, how do we pick? There are three common strategies:

StrategyHow it worksResult
GreedyAlways pick the highest-probability wordDeterministic but can be repetitive/boring
TemperatureDivide scores by T before softmax. T>1 = more random; T<1 = more focusedControls creativity vs. predictability
Top-pOnly consider the top words that cover p% of probability, sample among themAvoids unlikely nonsense while staying creative

This is why the same prompt can give different answers — with temperature > 0, the model randomly samples from probable next words rather than always picking the top one.

The Decode Loop

Generation is sequential — one word at a time:

1) You type:  "The sentiment of 'I like Jackie Chan' is:"
2) Model picks:  "positive"  (highest probability, or sampled)
3) Append:  "... is: positive" → feed the whole thing back in → get next word
4) Repeat until done (stop token or max length)

Task Prompts — One Model, Many Tasks

The same model handles completely different tasks — you just phrase them as "complete this text":

TaskHow you prompt it
Sentiment analysis"The sentiment of 'I like Jackie Chan' is:"
Q&A"Q: Who wrote 'The Origin of Species'? A:"
Summarization"TL;DR:" or "Summarize: ..."
Translation"Translate to Swedish: ..."
Coding"Write a Python function that ..."

No special mechanism per task — the model learned these patterns from seeing millions of similar examples during training.

KV Cache — Why It's Fast

Without optimization, generating word #100 would require re-processing all 99 previous words. The KV cache stores the keys and values from previous steps so they don't need to be recomputed:

Per layer, store: $\mathbf{K}_{1:k}$ (keys for all past tokens) and $\mathbf{V}_{1:k}$ (values for all past tokens).

For the next word ($k+1$):

  1. Only compute the NEW $\mathbf{q}_{k+1}, \mathbf{k}_{k+1}, \mathbf{v}_{k+1}$ for token $k+1$
  2. Compare new query against ALL cached keys (cheap — just one row)
  3. Append new key, value to cache
  4. Continue

Result: generating each new word takes constant time regardless of how long the text already is.

Bottom line: The model doesn't "understand" or "think." It assigns probabilities to possible next words based on patterns it learned from reading trillions of words of human text. The prompt steers which patterns activate. Temperature controls how adventurous it is. The KV cache makes it fast. That's ChatGPT.

Llama (Large Language Model Meta AI) is a family of open-weight Transformers from Meta. "Open-weight" means the trained parameters — all the $\mathbf{W}$, $\mathbf{E}$, $\mathbf{W}_Q$, $\mathbf{W}_K$, $\mathbf{W}_V$ matrices from Steps 3–5 — are publicly downloadable.

What's Inside the Model File?

The download contains three things:

  1. Weight matrices (99% of file size) — all the learned numbers from Steps 2–5:
    • $\mathbf{E}$ — embedding table (128K word vectors)
    • $\mathbf{W}_Q, \mathbf{W}_K, \mathbf{W}_V, \mathbf{W}_O$ per layer — attention (Step 4)
    • $\mathbf{W}_1, \mathbf{W}_2$ per layer — FFN knowledge (Step 5)
    • LayerNorm parameters
  2. Tokenizer — dictionary converting text ↔ token IDs
  3. Config — number of layers, dimensions, heads, etc.

Quantization — Making It Fit on Your Laptop

Full precision (16-bit) for a 3B model would need ~6 GB. Quantization rounds each weight to fewer bits, trading tiny quality loss for much smaller files:

The bundled server and Ollama both use GGUF format — a single file packaging weights + tokenizer + config.

What Ollama Does

Ollama is the inference engine — it loads the model file and runs Steps 3–6 on your hardware:

Your text
  → Tokenizer: "What is 5G?" → [3923, 374, 220, 20, 38, 30]
  → Embedding lookup (Step 2: IDs → vectors)
  → 32 Transformer blocks (Steps 4-5: attention + FFN)
  → Softmax → probability distribution (Step 6)
  → Sample with temperature/top-p (Step 6)
  → Detokenize → return text
  → Repeat (KV cache avoids recomputing past tokens)

Task 1.1 — Multi-Turn Chat: Why LLMs Need History

Difficulty: ★☆☆

Background

LLMs are stateless — each API call is independent. The model has no memory of previous requests. To create the illusion of a conversation, you must send the entire message history with every request. This is the fundamental constraint that drives all memory management in Lab 1.

Instructions

  1. Start a conversation with a system message and a user message: 
    curl -s http://localhost:11434/api/chat -d '{
  "model": "Llama-3.2-3B-Instruct-Q4_K_M",
  "messages": [
    {"role": "system", "content": "You are a helpful programming tutor."},
    {"role": "user", "content": "What is a variable in Python?"}
  ],
  "stream": false
}' | python3 -c "import sys,json; print(json.load(sys.stdin)['message']['content'][:300])"
  2. Continue the conversation — include the assistant's previous response in the history: 
    curl -s http://localhost:11434/api/chat -d '{
  "model": "Llama-3.2-3B-Instruct-Q4_K_M",
  "messages": [
    {"role": "system", "content": "You are a helpful programming tutor."},
    {"role": "user", "content": "What is a variable in Python?"},
    {"role": "assistant", "content": "A variable in Python is a name that refers to a value stored in memory..."},
    {"role": "user", "content": "Show me a simple example"}
  ],
  "stream": false
}' | python3 -c "import sys,json; print(json.load(sys.stdin)['message']['content'][:300])"
  3. Now try WITHOUT history — send only the follow-up: 
    curl -s http://localhost:11434/api/chat -d '{
  "model": "Llama-3.2-3B-Instruct-Q4_K_M",
  "messages": [
    {"role": "user", "content": "Show me a simple example"}
  ],
  "stream": false
}' | python3 -c "import sys,json; print(json.load(sys.stdin)['message']['content'][:300])"

What to Observe

  • With history: the model knows "Show me a simple example" refers to Python variables
  • Without history: the model has no idea what you're asking about — it might show an example of anything
  • The model "remembers" only because you sent the full history

Reflection Questions

  • Why must you send the entire conversation history with each request?
  • What would happen if you omitted the assistant's previous response from the array?
  • How does this relate to the concept of "context window" (max tokens)?
  • If each turn adds ~100-200 tokens, how many turns can fit in a 4096-token context window?
Key insight: This statelessness is why Task 1.3 (Memory Management) exists. The chatbot app must explicitly manage history — either client-side (JavaScript accumulates messages) or server-side (the server stores and trims history). Every memory strategy you'll implement is a solution to this fundamental constraint.

Task 1.2 — Temperature Experiment

Difficulty: ★☆☆

Background

Temperature controls how "creative" vs. "predictable" the LLM's output is. At temperature 0.0, the model always picks the highest-probability word (deterministic). At higher temperatures, it samples more broadly from possible words (more random, creative, but potentially less coherent).

Understanding temperature is essential for chatbot design: a customer service bot needs low temperature (consistent, predictable answers), while a brainstorming assistant benefits from higher temperature (diverse, surprising ideas).

Task 1.5 — Conversation Memory and Context Management

Difficulty: ★★☆ | Files: ai/memory.py, web/routes.py, ai/chat.py

Background

LLMs are stateless — they have no memory between requests. The illusion of a "conversation" is created by sending the full message history with every request. This means the conversation is limited by the model's context window (the maximum number of tokens it can process at once).

There are two architectural approaches to managing conversation history:

ApproachHow it worksProsCons
Client-side (current)JavaScript accumulates messages and sends the full array with each requestSimple; no server state; works with stateless/serverless backends; each browser tab has its own conversationNo server control over trimming; history lost on page refresh; can't apply smart strategies server-side; client can send arbitrarily large payloads
Server-side (this lab)Server stores messages in ConversationMemory; client sends only the new messageServer controls trimming/summarization; can monitor token usage; persists across page refreshes; enables advanced strategies (RAG over history)Requires session management; server holds state; more complex; single conversation per session unless you add session IDs

In production, server-side is the standard:

  • ChatGPT, Claude, Gemini — all store conversations server-side (accessible across devices, persist between sessions)
  • Customer service bots (Intercom, Zendesk, Drift) — server-side because conversations span days and require agent handoffs
  • LangChain/LlamaIndex — their memory modules (ConversationBufferMemory, ConversationSummaryMemory) are server-side patterns

Client-side history is mainly used in simple demos, stateless API wrappers, or privacy-focused apps that intentionally don't retain data.

Some production systems use a hybrid approach: the client sends the last few messages for immediate context (low latency, works offline), while the server maintains long-term memory with summarization and RAG retrieval for older context.

For this lab, we use server-side memory so you can observe and control exactly how context accumulates — this is the real-world pattern.

The current client-side code (in web/static/js/chat.js) that you will replace:

// Current approach: client accumulates history in a JS array
let history = [];

async function sendMessage(message) {
    history.push({ role: "user", content: message });

    const response = await fetch("/chat", {
        method: "POST",
        headers: { "Content-Type": "application/json" },
        body: JSON.stringify({ message: message, history: history }),  // sends full history
    });

    const data = await response.json();
    history.push({ role: "assistant", content: data.response });  // accumulates locally
}

After Step 1, the client will simply send { message: message } — no history management needed on the client.

Step 4: Implement Token-Based Trimming

Why token-based trimming is better than message-count trimming

The context window limit is measured in tokens, not messages — but messages vary wildly in size:

  • "Hi" = 1 token
  • A 3-paragraph explanation = 200+ tokens

With max_messages = 50, the system has no idea whether it's under or over the actual token budget:

  • 50 short messages ("yes", "no", "ok") = ~50 tokens total — wastes 4000 tokens of available context
  • 50 long messages (detailed explanations) = ~10,000 tokens — overflows the 4096 context window, causing errors or silent truncation

Token-based trimming (max_tokens = 3000) solves this by measuring in the same unit the LLM uses:

  • Short messages → more messages fit (maybe 100+)
  • Long messages → fewer messages fit (maybe 15)
  • Always stays within the actual context window budget — adapts automatically to message length

Step 5: Implement Sliding Window + Summary

The sliding window + summary approach keeps the last N messages in full and summarizes everything older into a single compact "memory" message. This preserves both recency (recent messages) and long-term facts (in the summary).

Why does Step 5 require modifying routes.py but Step 4 did not?

Token trimming (Step 4) is self-contained inside add_message() — it's a pure data operation (count characters, drop messages). No external dependency needed. When routes.py calls _memory.add_message(...), trimming happens automatically.

Summarization (Step 5) requires an LLM call to generate the summary text. The memory class doesn't have access to the LLM client on its own — it lives in the route handler. So routes.py must explicitly trigger summarization and pass the llm_client: 
# Token trimming: automatic inside add_message() — no routes.py change
_memory.add_message("user", message)  # trimming triggers internally

# Summarization: needs llm_client — routes.py must call it explicitly
_memory.add_message("user", message)
if _memory.needs_summarization():
    _memory.summarize_old_messages(llm_client)  # ← needs llm_client from routes.py
This is a common architectural pattern: operations that need external services (LLM, database, API) must be triggered from the layer that has access to those services.

@bp.route("/chat/stream", methods=["POST"])
def chat_stream():
    """
    Stream a chat response using Server-Sent Events.

    Accepts JSON: {"message": str, "history": list, "persona": str}
    Returns: text/event-stream with data: chunks
    """
    data = request.get_json()
    if not data or "message" not in data:
        return jsonify({"error": "Missing 'message' field"}), 400

    message = data["message"]
    history = data.get("history", [])
    persona = data.get("persona", None)

    from ai.chat import generate_response_stream
    from config import config
    from ai.models import create_client
    from ai.prompts import get_system_prompt

    backend = config.get("llm_backend", "ollama")
    llm_client = create_client(backend, config.get_all())

    if persona:
        system_prompt = get_system_prompt(persona)
    else:
        system_prompt = config.get("system_prompt", "You are a helpful assistant.")

    def generate():
        for chunk in generate_response_stream(message, history, llm_client, system_prompt):
            # SSE format: each message is "data: <content>\n\n"
            yield f"data: {chunk}\n\n"
        yield "data: [DONE]\n\n"

    return Response(

        mimetype="text/event-stream",

        }

async function sendMessageStreaming(message, history) {
    const response = await fetch('/chat/stream', {
        method: 'POST',
        headers: {'Content-Type': 'application/json'},
        body: JSON.stringify({message, history})
    });

    const reader = response.body.getReader();
    const decoder = new TextDecoder();
    let fullResponse = '';

    while (true) {
        const {done, value} = await reader.read();
        if (done) break;

        const text = decoder.decode(value);
        const lines = text.split('\n');
        
        for (const line of lines) {
            if (line.startsWith('data: ') && line !== 'data: [DONE]') {
                const chunk = line.slice(6);  // Remove "data: " prefix
                fullResponse += chunk;
                // Update the chat UI with partial response
                updateAssistantMessage(fullResponse);
            }
        }
    }
    
    return fullResponse;
}
